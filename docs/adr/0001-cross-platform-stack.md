# ADR-0001：选择 Tauri 2 跨平台桌面架构

- 状态：Proposed
- 日期：2026-07-22

## 背景

应用需要同时支持 macOS 和 Windows，包含完整主窗口、极简窗口、系统托盘、后台刷新、本地数据库、自动更新以及平台化玻璃效果。现有目录中的基金插件基于 Vue 2，包含可参考的数据字段和接口逻辑，但浏览器扩展结构不适合直接承担桌面后台任务与本地数据迁移。

## 决策

选择：

- Tauri 2 作为桌面外壳。
- Vue 3 + TypeScript + Vite 作为展示层。
- Rust 作为应用层、领域层和基础设施层。
- SQLite 作为本地持久化。
- 平台窗口效果通过独立适配器实现。

## 理由

- 一套界面代码覆盖 macOS 与 Windows。
- Tauri 使用系统 WebView，安装体积通常低于捆绑完整浏览器内核的方案。
- Rust 后台不依赖隐藏 WebView 的定时器，可稳定执行刷新和计算。
- Tauri 提供多窗口、托盘、权限、更新和打包所需能力。
- Vue 3 与现有 Vue 插件的认知模型接近，迁移界面和字段逻辑成本较低。
- Rust 领域层可以对收益计算和导入过程进行严格测试。

## 取舍

- 开发环境同时需要 Node 和 Rust；当前机器尚需安装 Rust 工具链。
- macOS 与 Windows 的玻璃效果并不完全一致，必须接受平台适配与降级。
- Tauri 使用不同系统 WebView，UI 自动化和兼容性测试必须覆盖两个平台。
- macOS 透明窗口相关 private API 可能影响 Mac App Store 路线，需要提前区分发布策略。

## 被否决方案

### 两套原生应用（SwiftUI + WinUI）

原生体验最好，但业务、数据和界面维护成本接近两倍，不符合持续迭代目标。

### Electron

生态成熟且一致性高，但会捆绑 Chromium，资源和安装体积更高。当前需求不需要 Node 主进程生态的额外能力。

### Flutter

跨平台能力良好，但现有 Vue 逻辑无法复用，桌面系统托盘、窗口特效和原生行为需要更多专项适配。

## 后续动作

1. 在 macOS 与 Windows 各完成一个窗口效果与托盘技术验证。
2. 确定 Mac App Store 是否为必要发布渠道。
3. 确认用户主要投顾平台，以决定 Phase 2 的首个适配器。
4. 技术验证通过后将本 ADR 状态改为 Accepted。
